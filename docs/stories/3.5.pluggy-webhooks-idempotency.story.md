# Story 3.5: Webhooks Pluggy e reconciliação idempotente

**Status:** Done  
**Epic:** [EPIC-3](../epics/epic-3-pluggy-carteira-real-e-saude-financeira.md)  
**Prioridade:** High  
**Dependência:** Story 3.4

## Objetivo

Receber notificações Pluggy com resposta rápida, deduplicar por `eventId` e processar a reconciliação em uma fila durável, sem depender de processamento síncrono dentro do webhook.

## Decisões

- O endpoint não exige sessão de usuário; autentica a origem por header secreto configurável.
- A resposta ao Pluggy contém somente `accepted` e `duplicate`; nunca retorna credenciais ou payload bruto.
- O payload recebido fica persistido apenas no backend para auditoria/reprocessamento.
- `item/updated`, `item/created`, `item/login_succeeded` e eventos de transação disparam uma nova sincronização do item.
- Eventos de erro/aguardando ação atualizam o estado da conexão sem tentar importar dados incompletos.
- O worker usa estados `RECEIVED`, `PROCESSING`, `SUCCEEDED`, `FAILED` e `IGNORED`, com retry limitado e backoff.
- O registro único por `eventId` torna os reenvios do Pluggy idempotentes.

## Critérios de aceitação

- [x] Endpoint HTTPS-ready valida header secreto e rejeita chamadas sem credencial com `401`.
- [x] Payload inválido é rejeitado sem persistência; payload válido recebe `202` rapidamente.
- [x] Reenvio do mesmo `eventId` não cria outro evento nem dispara outra sincronização.
- [x] Worker durável processa eventos fora do ciclo HTTP e atualiza a projeção Pluggy.
- [x] Falhas têm tentativas limitadas, backoff e estado persistido.
- [x] Eventos desconhecidos ou sem item local são auditados como `IGNORED`.
- [x] Nenhum segredo ou payload bruto é devolvido nas respostas ou logs operacionais.
- [x] Docker local inclui API, worker e configuração de polling/retry.
