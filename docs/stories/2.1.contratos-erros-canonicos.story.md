# Story 2.1: Contratos e erros canônicos

## User Story

Como mantenedor das interfaces de automação, quero uma fonte canônica de operações, schemas e erros, para que API, CLI e MCP expressem a mesma regra e o mesmo contrato.

## Status

Done

## Scope

- Definir catálogo compartilhado de operações e schemas runtime de input/output.
- Definir envelope de erro com `code`, `category`, `message`, `retryable` e detalhes de campos quando aplicável.
- Traduzir o contrato canônico para HTTP, CLI e MCP sem mover persistência para os adaptadores.
- Preservar a regra de rebalanceamento compartilhada existente.

## Out of Scope

- Alterar autenticação, writes ou provedores nesta story.
- Criar novas operações de produto.

## Acceptance Criteria

1. Inputs, outputs e erros das operações auditadas possuem validação runtime compartilhada.
2. Falhas esperadas incluem código estável, categoria e `retryable` sem depender do texto da mensagem.
3. API, CLI e MCP traduzem o mesmo erro canônico preservando seu código.
4. Nenhum schema público contém token, senha ou outra credencial.
5. Testes demonstram que payload ausente, extra ou incompatível é rejeitado de modo previsível.

## QA Results

### Review 2026-07-10 — Gate: FAIL

**Rastreabilidade dos critérios**

- AC 1 — **FAIL**: os inputs e o envelope de erro possuem validação runtime, mas todos os nove `outputSchema` do catálogo são `z.unknown()`. Assim, respostas incompatíveis das operações auditadas são aceitas sem validação.
- AC 2 — **PASS**: `operationErrorSchema` exige `code`, `category`, `message` e `retryable`, e o cliente normaliza erros HTTP legados.
- AC 3 — **FAIL**: CLI e MCP não preservam o erro canônico recebido. A CLI envolve falhas como `{ status, error }`, descartando `result.operationError`; ambos os MCPs recriam `Error` apenas com a mensagem e depois emitem `OPERATION_FAILED`.
- AC 4 — **PASS**: os schemas MCP derivados do catálogo não expõem token, senha ou credencial e rejeitam propriedades adicionais.
- AC 5 — **FAIL parcial**: há testes para inputs ausentes, extras e incompatíveis, porém não existe teste nem schema concreto que rejeite output incompatível; os testes atuais passam justamente porque os outputs são desconhecidos.

**Findings bloqueantes**

1. `packages/shared/src/contracts.mjs`: substituir `outputSchema: z.unknown()` por schemas concretos das nove operações e cobrir payloads válidos e incompatíveis em testes de contrato.
2. `packages/cli/src/index.mjs`: encaminhar o resultado completo (ou `operationError`) a `printError`, preservando o `code` retornado pela API.
3. `packages/local-mcp/src/index.mjs` e `apps/remote-mcp/src/index.mjs`: propagar `r.operationError` em vez de lançar um novo `Error` textual; adicionar teste que confirme preservação do código nas duas interfaces.

**Verificações executadas**

- `npm run test --workspace @paridade-risco/shared` — PASS, 6/6.
- `npm run typecheck` — PASS.
- Revisão manual de catálogo, schemas públicos, tradutor HTTP, CLI e MCPs — FAIL nos pontos acima.

**Decisão:** FAIL. Não foram feitas correções de código porque os defeitos exigem ampliar schemas e cobertura contratual. Pela autoridade de QA, somente esta seção foi atualizada; o status da story deve permanecer `Ready for Review` até novo ciclo de desenvolvimento e revisão.

### Re-review 2026-07-10 — Gate: FAIL

**Bloqueantes anteriores**

- Schemas das nove operações — **CORRIGIDO**: todos possuem `outputSchema` concreto e testes rejeitam payload incompatível.
- Preservação na CLI — **CORRIGIDO**: os comandos encaminham o resultado completo a `printError`, mantendo `operationError.code`.
- Preservação no MCP local — **CORRIGIDO para erros**: handlers propagam `r.operationError` e `mcpErrorResult` mantém o código canônico.
- Preservação no MCP remoto — **NÃO CORRIGIDO integralmente**: o cliente HTTP próprio descarta o corpo em respostas não-2xx (`data = null`) e sintetiza `operationError` apenas pelo status. Um código canônico específico enviado pela API é perdido antes de chegar a `mcpErrorResult`.

**Findings bloqueantes remanescentes**

1. `apps/remote-mcp/src/index.mjs`: ler e validar o envelope canônico em respostas não-2xx, preservando `code`, `category`, `message` e `retryable` fornecidos pela API; usar fallback por status somente para respostas legadas ou inválidas.
2. `packages/local-mcp/src/index.mjs` e `apps/remote-mcp/src/index.mjs`: os handlers não aplicam os `outputSchema` concretos. O MCP local chama `apiGet` sem o nome da operação e o remoto usa cliente próprio sem validação de output. Portanto, um payload HTTP 200 incompatível ainda é devolvido como sucesso por ambos os MCPs.
3. Adicionar testes nos fluxos reais dos adaptadores, não apenas no helper `mcpErrorResult`: (a) código canônico específico vindo da API permanece igual no MCP remoto; (b) output 200 incompatível é rejeitado no MCP local e remoto.

**Verificações executadas**

- `npm run test --workspace @paridade-risco/shared` — PASS, 9/9.
- `npm run typecheck` — PASS.
- `git diff --check` — PASS.
- Comparação manual dos nove schemas com as rotas da API — compatível para os formatos auditados.
- Rastreamento CLI/MCP do erro e validação de output — FAIL nos dois fluxos remanescentes acima.

**Decisão:** FAIL. Os schemas concretos e a CLI foram corrigidos, porém AC 1 e AC 3 ainda não são satisfeitos por todos os adaptadores. Nenhuma correção de código foi aplicada por QA.

### Final re-review 2026-07-10 — Gate: PASS
