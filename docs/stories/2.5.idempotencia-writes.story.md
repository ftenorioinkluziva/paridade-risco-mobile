# Story 2.5: Idempotência de writes

## User Story

Como cliente da API, quero repetir uma requisição após timeout sem duplicar registros, para preservar a integridade de transações, fundos e cestas.

## Status

Done

## 🤖 CodeRabbit Integration

> **CodeRabbit Integration**: Disabled
>
> CodeRabbit CLI is not enabled in `core-config.yaml`. Quality validation will use manual review process only.

## Scope

- Suportar chave de idempotência vinculada a usuário e operação nos três endpoints auditados.
- Persistir/reutilizar o resultado da primeira execução bem-sucedida.
- Tratar concorrência, reuso com payload diferente e expiração/retenção conforme decisão arquitetural aprovada.

## Out of Scope

- Reconciliação automática de duplicatas históricas.

## Tasks / Subtasks

- [x] Aplicar idempotência à criação de transações, fundos e cestas (AC: 1, 3, 4).
- [x] Rejeitar a mesma chave com payload semanticamente diferente (AC: 2).
- [x] Cobrir retries sequenciais e concorrentes (AC: 1–4).
- [x] Documentar migração/rollback, executar gates e atualizar a File List.

## Acceptance Criteria

1. Mesma chave, usuário, operação e payload resultam em um único write e resposta equivalente.
2. Mesma chave com payload diferente retorna conflito canônico sem novo write.
3. Requisições concorrentes com a mesma chave não criam duplicatas.
4. Chaves não permitem colisão entre usuários ou operações.
5. O comportamento sem chave mantém compatibilidade explicitamente definida pela arquitetura.

### Completion Notes List

- Persistência com retenção de 30 dias e unicidade por usuário, operação e chave.
- Payload canônico protegido por SHA-256; reuso divergente retorna `IDEMPOTENCY_PAYLOAD_CONFLICT` (409).
- Advisory lock transacional serializa chamadas concorrentes e o registro da resposta participa da mesma transação do write, garantindo rollback atômico.
- Ausência de `Idempotency-Key` mantém o comportamento compatível, executando exatamente um write sem persistir chave.
- A migração contém instrução explícita de rollback (`DROP TABLE idempotency_records`).
- A suíte de integração é opt-in (`test:integration`) e exige o container `paridade-risco-db`; a suíte root padrão permanece independente desse ambiente.
