# Story 2.2: Validação de respostas externas

## User Story

Como operador do sistema, quero que toda resposta externa seja validada antes do uso, para impedir dados financeiros incorretos e falhas opacas.

## Status

Done

## Scope

- Validar content type, parsing JSON e schema das respostas HTTP.
- Validar envelopes recebidos pela CLI/MCP e payloads dos provedores financeiros.
- Mapear timeout, resposta malformada e schema incompatível para erros canônicos.

## Out of Scope

- Troca de provedor ou mudança das regras financeiras.

## Acceptance Criteria

1. Nenhuma resposta desconhecida é consumida apenas por type assertion ou acesso direto sem validação.
2. Content type ou JSON inválido gera erro canônico não retryable ou retryable conforme a causa documentada.
3. Timeout e indisponibilidade são distinguíveis de schema incompatível.
4. Fixtures de falha comprovam que dados inválidos não chegam à regra financeira.

## QA Results

### Review Date: 2026-07-10

### Reviewed By: Quinn (Test Architect)

### Code Quality Assessment

A validação dos provedores Yahoo/BCB e do fluxo HTTP GET está bem encapsulada e produz erros canônicos distinguíveis. Contudo, a implementação não cobre toda a fronteira declarada pela story: `apiPost` aceita qualquer JSON de sucesso e a CLI acessa diretamente `result.data.token` e `result.data.user.id` no login. Portanto, uma resposta HTTP 200 incompatível ainda atravessa a fronteira sem validação runtime, violando o AC 1.

### Refactoring Performed

Nenhum. A revisão foi estritamente consultiva e não alterou código de produção ou testes.

### Compliance Check

- Coding Standards: ✓ `npm run lint` concluiu com 0 erros e 7 warnings preexistentes fora do escopo.
- Project Structure: ✓ Os validadores de provedores estão isolados na fronteira da API e os contratos de operações GET permanecem no pacote compartilhado.
- Testing Strategy: ✗ Os testes cobrem GET, Yahoo e BCB, mas não exercitam resposta 200 incompatível no `apiPost`/login.
- All ACs Met: ✗ AC 1 não atendido integralmente; ACs 2–4 possuem evidência automatizada adequada para os caminhos implementados.

### Requirements Traceability

- AC 1: Parcial — Given uma resposta GET ou de provedor incompatível, when ela cruza a fronteira, then o schema a rejeita; porém o mesmo não ocorre no login via `apiPost`.
- AC 2: Coberto — HTML e JSON truncado geram `UPSTREAM_CONTENT_TYPE_INVALID` e `UPSTREAM_JSON_INVALID`, ambos sem exposição do corpo.
- AC 3: Coberto — timeout gera `UPSTREAM_TIMEOUT` retryable, distinto de `UPSTREAM_SCHEMA_INVALID` não retryable.
- AC 4: Coberto — fixtures Yahoo/BCB incompatíveis são rejeitadas antes da transformação financeira.

### Improvements Checklist

- [ ] Adicionar contrato runtime para a resposta de login e validar o payload de sucesso no `apiPost` antes de devolvê-lo à CLI.
- [ ] Adicionar teste de failure injection com HTTP 200 e payload de login incompatível, comprovando que token/user não são acessados.
- [ ] Disponibilizar ou documentar o gate de build exigido pela Constituição; `npm run build` falha porque não existe script raiz.

### Security Review

A ausência de validação da resposta de login é bloqueante: uma resposta malformada ou adulterada pode ser persistida como configuração de autenticação. Os novos erros de provedores não incluem o corpo externo, reduzindo risco de vazamento nos cenários cobertos.
